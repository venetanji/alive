## Established observations

- `experiments/phase2-20261028/master/cloud-f0f7871/windows-job-original.log:1037` records automatic DLL exports and creation of `ultra_native.dll` and its import library. The release script builds and smoke-checks the native library, sets its build directory on PATH, stages the DLL beside the target output, then runs the Ultra Windows MSVC release Rust tests (`apps/ultra/scripts/release.py:312`, `:320`, `:327`, `:335`, `:341`). This describes staging, not proof of the exact image mapped by each process.
- The log reports the direct resolver test passing at line 1678, and eight failures, 275 passes and four ignored at lines 1933-1943. The preflight test directly asserts that `native::master_capability()` is `None` (log line 1908); child process failures include unavailable Master and `UNSUPPORTED` (lines 1788, 1833, 1878, 1900, 1928). Not all eight literally return `UNSUPPORTED`; some fail earlier preflight, unwrap, or expected-error assertions.
- Application `native::master_capability` caches `resolve(alive_session_state_v2 as pointer)` in a `OnceLock<Option<_>>` (`apps/ultra/src-tauri/src/session/native.rs:7`), so an initial failure persists per process. Host preflight rejects non-unity gain without it (`apps/ultra/src-tauri/src/session/host.rs:26`). Seven failed tests run their actual fixture in fresh child processes (`native_master.rs:37`); this rules out explaining all failures solely as one poisoned parent cache.
- The direct test uses a **separate** declaration of the same symbol, with `#[link(name="ultra_native")]` (`native_master.rs:115`); the application declaration in `native.rs:130` has no link attribute, although `build.rs:6` links the dylib globally. The test calls `resolve` directly, never testing the production `OnceLock` path. Its expectation is conditional on `ALIVE_MASTER_EXPECT_UNAVAILABLE` (`native_master.rs:122`); the retained log does not itself report that environment variable. If unset, its pass establishes that its own anchor resolved all six exports and passed the limits checks in that process; if set, its pass means the opposite. The old-library tests also return immediately when that variable is unset (`session/tests.rs:178`, `desktop.rs:1120`), so their logged pass alone does not establish a fallback fixture ran.

## Mechanism and uncertainty

The contradiction is explained at the source level: the two paths do not use the same extern declaration or cached result. `resolve` requires an anchor's containing module, an identical `alive_session_state_v2` export, six same-owner Master exports, and an exact successful limits response (`native_master.rs:45`, `:94`, `:100`). Any failure becomes `None`; the log records no branch, addresses, module paths, last error, symbol lookups, or limits values. Consequently it does **not** establish which check failed or why the declarations produced different results. No missing export should be inferred; subject to the environment caveat above the direct positive resolution would instead show those exports and limits working for its own anchor in its process.

The leading testable hypothesis is that MSVC produces a DLL import thunk for the application declaration while the explicit linked declaration resolves to the actual DLL address. If so, `GetModuleHandleExW(FROM_ADDRESS)` identifies the executable for the former, and the anchor/export equality check rejects it before Master resolution. Different images or an environment-dependent result remain alternatives until measured. Neither the source nor the retained log proves the thunk or address inequality. Rust Reference documentation retrieved via Context7 says `#[link]` applies to declarations within its extern block and Windows `dylib` linking uses an import library; it does not promise specific function-pointer code generation. Context7's Windows Rust API documentation says `GetProcAddress` returns the address of an exported DLL function; this does not establish the actual address obtained by either declaration in this build.
