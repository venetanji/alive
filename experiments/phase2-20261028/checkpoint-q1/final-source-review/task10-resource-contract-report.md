## Alternative: versioned catalog locator

The earlier preflight proposes a bounded, owner-only catalog locator for these three immutable catalog identities, plus the existing source fingerprint and manifest identity/version, with a fresh instance identity per load. Persist a versioned, explicitly discriminated bundled locator carrying only a known catalog ID; retain the existing path form unchanged for picker-loaded and existing sessions. Resolve the catalog ID at each prepare/open against the current installed resource root, independently of project location. The UI passes only the catalog ID and explicit captured target/revision; the owner checks the allowlist, expected kind, manifest and pinned fingerprint, then candidate graph and native admission before installation. Never accept a UI-provided path/hash/kind as authority and never silently update a saved hash. Catalog IDs must remain stable and mapping must be fixed by the application, not by untrusted session data.

A saved fingerprint pins the exact canonical source content selected, so moving the installation can resolve the same resource from its new root; upgrading to different content must fail visibly unless the old matching resource remains available or the user explicitly replaces it. Specify no automatic catalog aliasing or silent migration to a new source. Missing/changed/wrong-kind/corrupt resource fails with an actionable message, leaves the running session unchanged, and supports recovery by restoring the matching installation/resource or an explicit, separately designed replacement flow. It does not promise a general in-app repair of an unopened file. Never resolve old path-based references to a catalog merely by matching name/path; preserve their existing semantics. Save As retains the catalog locator and fingerprint while continuing existing rebasing for ordinary paths. Strict serde and current path-based preparation require an explicit compatible wire/version strategy, including old-reader behavior and round-trip for both v3 and v4/v5; this is a real format/owner change, not an already available facility. A versioned saved-session extension must not erase Master, histories, mixer, bypass, bases or automation.

Comparison: retaining the resolved installation path plus fingerprint requires no new wire and is sufficient only while that exact installed path remains valid. Save As rebase does not make installation moves/upgrades portable; restoration at the old path or explicit replacement is required, and Open failure prevents promising current UI repair. It is a narrower possible decision if the controller explicitly accepts those limits, but does not provide the proposal's stable installed locator. A managed source copy preserves content across application upgrades, but introduces storage ownership, atomic creation/cleanup, collisions and lifecycle rules. The catalog-locator proposal handles installed-resource relocation only, not portable arbitrary picker devices, version archive distribution, or full mixed project portability. Do not use a made-up path sentinel unless its validation, noncollision, representation and backwards compatibility are explicitly designed and reviewed.

Catalog metadata should include expected manifest ID/version, kind and a committed canonical fingerprint generated/verified from the actual included file, not trust the first observed bytes. Pinning allows the owner to refuse a changed packaged source even on a first load. Decide versioned catalog mappings and any retention policy before release; an upgrade that removes old content is an explicit recoverable failure, not an automatic conversion.

## Smaller candidate: managed bundled-source store

The earlier preflight `.superpowers/sdd/2026-10-28-phase2-live-max/task10-bundled-reference-preflight.md` correctly identifies AppImage mount lifetime and proposes a v6 logical binding, including translating the trusted New template. A v6 wire is not inherently necessary to avoid that mount: for a catalog load and trusted New-template creation, an owner-controlled durable per-user application-data store can materialize the verified, original bundled `.ultra` source under a content-addressed name and use the existing ordinary filesystem `path` and canonical `sourceSha256`. Existing prepare, Save As and Open can then operate without interpreting a new locator, provided the store remains in place. Recommend this as the smallest candidate for the controller to freeze if its bounded persistence tradeoffs are acceptable. It is a managed copy of only the three owner-allowlisted bundled sources, not a general project collector or a promise that projects travel with arbitrary dependencies.

Before accepting a catalog load, owner resolves an allowlisted packaged resource, reads and validates the original patch and pinned canonical fingerprint, checks expected manifest identity/version/kind, then stages the source outside the mount under a deterministic fingerprint-derived filename. Create with atomic no-clobber/rename semantics in a private durable store, reject or safely handle symlinks and collisions, and re-read/revalidate any existing destination rather than overwrite it; retain the original parsed patch identity and never persist live-base-mutated prepared patch. The path stored in each fresh device reference is the resolved durable store path, with current instance identity and fingerprint. Existing candidate prepare, kind checks and native admission still run before install, with generation/revision checks and unchanged score on failure. A failure can leave an unreferenced immutable cache entry, but never a changed session, overwritten existing file or partially published source; define lifecycle explicitly and do not garbage-collect entries while sessions/history may reference them. Recheck the actual on-disk source through normal prepare on Save/Open; altered/missing managed data refuses and requires restoration of matching content. No silent refingerprinting or fallback to a different revision.

The trusted New flow is equally critical: after verifying only the known template's expected Subtractive source and fingerprint, rebind its references to the managed file in the prospective new session before install/save, preserving Master reset and all per-instance fields. Do not rewrite arbitrary opened v1-v5 files, including old saved paths into an AppImage mount; they retain current semantics and may fail if their original source disappeared. This proposal keeps the score and envelope formats unchanged and gives old readers ordinary paths, but does not make a session independent of the per-user data directory: deleting/moving it, changing OS account or transferring the project still breaks references. A changed bundled version can coexist at a new fingerprint path, preserving the old revision only as long as the store is retained. Restoring a deleted store entry from matching shipped bytes may be offered only as a separately specified explicit recovery operation; existing Open itself does not repair it. A store copied from the bundle is locally writable in principle, so immutable is an owner policy, not OS-enforced integrity; fingerprints detect changed content. Do not expose editing it as a source file; document hosted structural editing and explicit export/Replace separately.

This is smaller than v6 in schema and resolver plumbing, but requires durable store location/permissions, cross-platform and AppImage validation, bounded resources, crash-safe publication and a no-deletion policy. Fingerprint collisions or semantically identical JSON with different bytes need an explicit policy: verify canonical patch hash and expected manifest, accept an already stored matching canonical patch without byte equality, and reject a mismatched occupant; do not use raw byte hash as the session hash. Ensure stored file is a bounded, valid original saved Ultra document and that the copy exactly corresponds to the verified bytes; avoid check/copy time-of-check races. Duplicate loads deduplicate store content but retain distinct instance IDs and bases. Session Save As must still reject overwriting the managed dependency, and previous path-based references remain subject to the same safeguards. This does not preimplement Task 13: normal Save copies no arbitrary project sources, and no collect/export/relocate feature is introduced.

The release generator itself explicitly includes only the example session and Subtractive in its own resource map; the base config declares the effects too. As the previous preflight recommends, explicitly add and verify both effects in the release generator; do not assert their final absence without establishing Tauri's effective map and inspecting exact package payloads. Both candidate contracts require that staging and real package tests. V6 gives clean logical identity and relocation across per-user store moves but needs new wire, validation and resolver propagation; managed copies trade that breadth for dependence on long-lived user data and retained content. The choice is the controller's; neither is frozen.
